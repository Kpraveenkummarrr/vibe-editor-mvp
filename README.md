# Vibe Editor — MVP

An AI-powered website editor: select an element on the live preview (or describe a
page-wide change), ask the assistant for an edit, watch it apply instantly, review it
in local version history, inspect the underlying code, check for issues, and
build/publish a live site. Built with React + Vite.

Three things this app does for real, not as a mock:

- **LLM-powered editing** — a real LLM call (OpenRouter, free tier) when an API key is
  configured, via a server-side proxy so the key never reaches the browser. Without a
  key, it falls back to a deterministic local rule-based engine — always fully
  functional, never pretending to call a model it isn't calling.
- **Local version control** — every applied edit (AI or manual) is a full, restorable
  snapshot kept in `localStorage`. Restoring a past version never deletes history —
  it's a non-destructive checkout, like `git revert`.
- **Netlify deployment** — the "Publish" button deploys the current page to a real,
  live Netlify site via Netlify's deploy API, server-side, using your own token.

See "Enabling live AI edits" and "Enabling Netlify publishing" below to turn the first
and third of these on.

## Setup

```bash
npm install
npm run dev
```

Open the printed local URL (default `http://localhost:5173`).

```bash
npm run lint    # ESLint
npm run test    # Vitest (AI engine + validator unit tests)
npm run build   # Production build
```

## Enabling live AI edits (optional)

1. Create a free account at [openrouter.ai](https://openrouter.ai) and generate an API
   key at [openrouter.ai/keys](https://openrouter.ai/keys) (free models require no
   payment method).
2. Copy `.env.example` to `.env.local` and paste the key into `OPENROUTER_API_KEY`.
3. Restart `npm run dev`. The assistant panel header will switch from a "Local engine"
   badge to a "Live AI" badge, and edits will be generated by the model.
4. For the deployed app, add `OPENROUTER_API_KEY` (and optionally `OPENROUTER_MODEL`)
   as environment variables in the Vercel project settings — the same `/api` functions
   run there automatically, no extra config needed.

If the configured model has been deprecated, set `OPENROUTER_MODEL` to any other free
model from [openrouter.ai/models?max_price=0](https://openrouter.ai/models?max_price=0).

## Enabling Netlify publishing (optional)

1. Generate a personal access token at
   [app.netlify.com/user/applications#personal-access-tokens](https://app.netlify.com/user/applications#personal-access-tokens)
   (free Netlify account, no card required).
2. Copy `.env.example` to `.env.local` (if you haven't already) and paste the token
   into `NETLIFY_API_TOKEN`.
3. Restart `npm run dev`. Clicking **Publish** in the top bar now deploys the current
   page as a standalone HTML file to a real Netlify site and returns a live
   `https://*.netlify.app` URL. Publishing again redeploys the same site (its id is
   remembered on the project) instead of creating a new one each time.
4. For the deployed app, add `NETLIFY_API_TOKEN` as an environment variable in the
   Vercel project settings.

Without a token, Publish shows setup instructions instead of pretending to deploy, and
you can still use "Download HTML" to get the same file to host anywhere yourself.

## How it works

**Select → describe → apply → review → publish**

1. Click any element in the preview canvas (edit mode) — it's outlined and shown in
   the assistant panel as "Editing element". Click a suggested prompt or type your own
   ("make this more premium", "shorten the headline", "use a darker green"). Toggle
   **Build** (applies immediately) vs **Plan** (the assistant proposes the change as
   text first; you click "Apply this change" to actually run it) above the input.
2. The request is sent to `/api/ai-edit`. If a live model is configured, it returns a
   small structured JSON action (target hint, text replacement, style changes, brand
   color, reply) — validated and sanitized server-side against an allow-list before
   ever reaching the browser (see `api/_lib/openrouter.js`). Otherwise (or if that call
   fails for any reason), `src/ai/intentParser.js` classifies the request locally into
   one of a fixed set of intents instead.
3. Either way, the action is applied against the current HTML/CSS — targeting the
   selected element (via a stable `data-vibe-id` re-derived from the stored HTML, see
   `utils/domIds.js`) or a sensible page-wide fallback — by `ai/applyLLMAction.js` or
   `ai/applyAction.js` respectively.
4. The result updates `files["index.html"]`/`files["styles.css"]` in the central
   project state and records a full **version** (snapshot before + after) in
   `project.changes`, viewable and restorable from the History tab.
5. The preview iframe re-renders from the updated files; an injected script reports
   clicks back to the parent via `postMessage` so selection keeps working after every
   re-render.
6. **Build** validates and bundles the page into a downloadable standalone HTML file.
   **Publish** does the same, then deploys that file to Netlify and returns a live URL.

## Architecture

```
api/
  ai-edit.js          Vercel function: forwards a request to OpenRouter (POST)
  ai-status.js         Vercel function: reports whether a live AI key is configured (GET)
  publish.js            Vercel function: deploys the built page to Netlify (POST)
  publish-status.js      Vercel function: reports whether a Netlify token is configured (GET)
  _lib/openrouter.js  Prompt building, model call, response sanitization (shared)
  _lib/netlify.js      Site creation + zip deploy via the Netlify API (shared)

src/
  state/            ProjectContext (React context + useReducer) + localStorage persistence
  ai/                intentParser + applyAction (local engine), applyLLMAction (live
                     engine applier), engine.js (tries live, falls back to local) + tests
  utils/             domIds (selection/mutation), validateHtml (Issues panel),
                     highlight (code syntax highlighting), download, storage, publish
  data/              default demo project content (a small business site)
  components/
    TopBar.jsx                project switcher, save status, Build, Publish
    AssistantPanel.jsx        chat, Build/Plan toggle, suggested prompts, selection indicator
    PreviewWorkspace.jsx      iframe canvas, edit/preview + viewport toggles
    RightPanel/               Files / Code / History / Issues tabs
    modals/                   Rename, Import/Export, Build, Publish
    ui/                       Button, Badge, EmptyState, SegmentedControl, Modal
```

During `npm run dev`, a small Vite middleware (`vite.config.js`) mirrors the same
`/api` functions locally so the flow is identical in dev and on Vercel — no `vercel
dev` required.

State shape (per project, all persisted to `localStorage`):

```
Project
├── files            { "index.html", "styles.css", "script.js" }
├── customFiles       user-created extra files
├── selectedElement   { vibeId, tag, text } | null
├── editorState        { mode: edit|preview, viewport, rightTab, chatMode: build|plan }
├── changes            version history: [{ summary, timestamp, snapshotBefore, snapshotAfter }]
│                       — restoring is non-destructive, like git revert
├── issues             derived from files via utils/validateHtml.js
├── buildState          { status, lastResult, lastBuildAt }
├── publishState         { status, url, siteId, lastPublishedAt, error }
└── chat                assistant messages (source: "llm"|"local"; plan-mode ones carry
                        a pendingEdit until applied)
```

Multiple projects are supported (switch/duplicate/rename/reset/import/export from the
project menu in the top bar).

## Safety notes on the live AI path

The model never returns or writes raw HTML/CSS/JS directly — only a small structured
action (a CSS selector hint, plain text, a hex color, and a handful of inline style
properties from a fixed allow-list). `api/_lib/openrouter.js` validates every field
server-side (rejecting `javascript:`/`expression()`/arbitrary `url()` values, capping
string lengths) before it's sent to the browser, and `src/ai/applyLLMAction.js`
re-validates the target exists before mutating anything. This keeps the live path as
safe as the local rule-based engine while allowing far more flexible language
understanding.

## Notes

- Kept intentionally scoped as an MVP: no auth, no collaboration/multiplayer, no
  real-time multi-user sync — the chat → AI action → preview → version history →
  build/publish loop is the focus.
- No heavy code-editor or highlighting dependency (e.g. Monaco/CodeMirror/Prism) —
  `utils/highlight.js` is a small regex-based highlighter, kept lightweight on
  purpose; swap it for a richer editor later without changing how files are stored.
- Element selection uses a `data-vibe-id` attribute assigned deterministically
  (pre-order traversal) when building the preview, and re-derived the same way when
  applying an edit — so it never needs to be persisted into saved project files.
- Publishing zips the built page with `jszip` server-side and deploys it via Netlify's
  "deploy without git" zip endpoint — the only added runtime dependency, and only used
  in `api/`, never bundled into the client.
